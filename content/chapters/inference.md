A batch narrator can finish a ten-second passage in two seconds and still leave a two-second gap before the first word. In an interactive reader the first deadline is audible onset. Subsequent deadlines are the moments at which the device will exhaust its buffer. A workload can meet either deadline while missing the other.

## Draw the serving graph before optimizing it

In a cascade, time-stamp capture, transport, streaming encoder updates, endpoint decision, final transcript, retrieval, first speakable phrase, synthesis, transport back and device presentation. A token announcing an internal tool request does little for audible onset. A direct speech model can collapse several stages but still has input framing, model scheduling, codec decoding and device playout. Instrument the boundaries the implementation actually exposes, and retain model versions and trace IDs. [OpenTelemetry trace concepts](#source/sy-trace)

Here is an **illustrative timeline**, in milliseconds from the last user speech sample. Endpoint confidence becomes sufficient at 180 and recognition’s final words are ready at 230. Assume they run independently and answering waits for both. Retrieval takes 40, a speakable phrase 90, synthesis to first chunk 85, and output transport plus playout 40. The first audible sample arrives at **max(180, 230) + 40 + 90 + 85 + 40 = 485 ms**. Cutting endpoint time by 80 changes nothing in this trace. In another graph the final decoder may be triggered only after the endpoint, making those stages serial. Measure per-turn critical paths; adding separate stage p95s does not give a turn p95. The [latency lab](#lab/latency) lets you change assumptions on a modeled path.

## Budget memory and bandwidth separately

Loading a model includes fetching or opening the artifact, verifying its digest, materializing weights, transferring them, compiling or selecting kernels and warming representative shapes. Cold-start and warm-turn histograms answer different questions. Keep an instance unready until a representative probe completes, and measure the idle cost of keeping it warm.

A billion 16-bit weights occupy about 2 GB in decimal units before workspace, activations and state. If one low-batch decoder iteration must stream all those bytes from device memory at an **assumed sustainable** 160 GB/s, transfer alone needs at least 2/160 s = 12.5 ms. That bound changes when cache residency or batching changes the bytes transferred per emitted token. More arithmetic units help only when arithmetic is limiting. FlashAttention’s tiled exact computation illustrates how reducing traffic between memory levels can improve an attention operation. [FlashAttention](#source/sy-flash)

## Identify the state owned by each stage

For a conventional autoregressive attention decoder, each retained token stores a key and a value. With 24 layers, 8 key/value heads per layer, head dimension 128, and 2 bytes per element, a 1,024-token sequence takes **2 × 24 × 8 × 128 × 2 × 1,024 = 96 MiB** of KV state. This excludes weights and allocator overhead. Sequence growth and cancellation make allocation irregular. PagedAttention manages KV blocks to reduce waste. Iteration scheduling lets finished sequences leave and new ones join between decode steps. A shared prefix cache requires identical inputs, model, adapter and allowable sharing scope. Namespace it by authorization boundary. [PagedAttention](#source/sy-paged) · [Orca](#source/sy-orca)

Model family matters. A streaming encoder may retain left-context frames or convolution state. Its right-context requirement creates algorithmic delay even with an idle GPU. A transducer keeps prediction-network state and beam hypotheses. A convolutional vocoder uses receptive-field context at chunk seams. A diffusion sampler pays for its chosen denoising iterations. A codec-token transformer can use token KV caching if its attention permits it; the decoder converting tokens to waveform has its own state. Preserve timestamps and stage-specific caches when one session moves workers.

Weight quantization reduces representation size, while activation quantization changes intermediate precision as well. Scale metadata, kernel availability and conversion overhead determine actual speed. Test substitutions on names and numbers, speaker identity, buzzing at quiet phonemes and seam clicks, as appropriate for the stage. SmoothQuant studied particular transformer workloads; a waveform generator needs an audio-quality gate. [SmoothQuant](#source/sy-smooth)

## Schedule for playout headroom

Dynamic batching can collect compatible stateless chunks for a short window. Waiting to fill a batch spends latency budget. Retain per-session ordering and state ownership for a stateful stage. Schedule by remaining playout headroom or deadline, age low-priority work, and bound queued audio. Give an interactive question priority over speculative future narration. On cancellation, invalidate queued audio and release obsolete state so generation stops consuming capacity. A dropped request should receive an explicit recoverable response. [Triton batchers](#source/sy-triton)

The real-time factor **RTF = service seconds / audio seconds**. In an illustrative unbatched worker, a 200 ms chunk taking 24 ms gives RTF 0.12. Six continuously speaking streams each deliver five such chunks per second. The offered service demand is 6 × 5 × 0.024 = 0.72 worker-seconds per wall second. Eight would offer 0.96, leaving little room for synchronized arrivals, allocator stalls or other stages. This calculation estimates utilization. Sweep offered concurrency, arrival jitter, utterance length and cancellations while measuring queue age, audible onset and buffer underruns. Report admitted and failed sessions as well as percentiles.

For each run, trace CPU preparation, device copies, kernel execution and output encoding. Use device events for asynchronous GPU work; timing a host enqueue alone measures submission. If memory bandwidth is saturated while compute units wait, inspect bytes transferred per chunk before changing batch size. If both are mostly idle but queue age rises, inspect scheduler limits, state affinity and upstream CPU work.

For Murmur, suppose a hypothetical worker costs **$2.40 per provisioned hour**, can meet its deadline on six simultaneous continuous streams, and delivers 75% of that six-stream capacity as useful heard audio over an hour. Useful output is 60 × 6 × 0.75 = 270 listener-minutes. Compute cost is $2.40/270 ≈ $0.0089 per heard minute. This is an invented sensitivity example. Count idle reservations, storage, ingress/egress charges when applicable, failed work, engineering and support in an actual comparison. Replacing *heard* minutes with generated minutes hides the cost of cancelled narration.

## Exercise · find the first missed deadline

Create two profiles, a long narration stream and a short interrupting question. In the [latency lab](#lab/latency), vary service delay and predict the output buffer needed to absorb a late first chunk. A buffer buys continuity at the expense of startup or trailing old audio. In the [interruption lab](#lab/interruption), observe what happens to generated but unheard content. On a real system trace one cold run and at least 30 warm repetitions per condition, then increase concurrency until p95 or underrun rate breaches a predeclared target. Include timeouts and run longer for tail estimates. For local profiling, whisper.cpp provides CPU and accelerator backends; pin a revision and model, record hardware, thermal state and quality. This optional real-ASR experiment requires a model download. [whisper.cpp](#source/sy-whisper)

For failover, save the document revision, last confirmed heard anchor and acknowledged tool operations. On worker loss, begin a new epoch and rebuild model state from consented bounded context. Regenerate from the agreed replay boundary. A brief repetition is measurable; silently jumping past buffered words is harder for a listener to repair.

## Check your reasoning

**Why might a smaller quantized model have the same onset latency?** Endpointing or queue wait may dominate the critical path, or quantization may lack an efficient target kernel. Compare client spans and warm service times at matched audio quality.

**What should an on-device benchmark run after the first successful turn?** A sustained session with realistic concurrent workloads, memory pressure, battery and thermal constraints. A short run with a cool device can hide persistent deadline misses.
